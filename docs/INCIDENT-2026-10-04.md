# Incident report: hard reset, HDFS stuck in safe mode (2026-10-04)

## Summary
Three unclean VM restarts in one night (01:18, 01:45, 02:39). The last, around 02:36, left HDFS in safe mode and
`hadoop-hdfs.service` failed, which stopped YARN, HiveServer2 and the Spark job. Kafka-side ingestion kept running.
No data was lost: Spark resumed from its checkpoint and re-read the affected batch from Kafka.

| 03:04 | Spark commits batches 221–223: recovery confirmed |

## Root cause
1. **Trigger:** a hard VM reset while HDFS was writing. XFS lost unflushed data, leaving 7 block files at 0 bytes with
   0-byte `.meta` (blocks `blk_1073743279`, `…280`, `…283`–`…287`).
2. **Why safe mode never ended:** the NameNode expected 721 blocks, needed 99.9 % (720) to be reported safe, but the
   zero-length replicas mismatched the recorded lengths and were marked corrupt: 714 safe blocks, below the threshold.
   The "723 blocks reported" figure was the raw DataNode count and included the corrupt and under-construction ones.
3. **Why it became an outage:** the unit ran `hdfs dfsadmin -safemode wait` as a start step with a 300-second limit.
   When that timed out, systemd marked the unit failed and killed the NameNode and DataNode too. Safe mode itself had
   done no harm; the unit design turned it into a full HDFS stop. `Requires=` then took down YARN, Hive and Spark.

The cause of the hard reset itself is **not established** (the previous boot's journal was not available).

## Affected data
The 7 corrupt files were all small and recent:
- 2 Tez scratch files (disposable),
- the Spark checkpoint trio for batch 221 (`offsets/221`, `commits/221`, `_spark_metadata/221`),
- 2 Parquet files (one in `severity=normal`, one in `severity=warning`).

## Recovery
1. `hdfs dfsadmin -safemode leave` (clears the flag, deletes nothing).
2. Moved the 7 files to a quarantine directory with their original paths (not deleted).
3. Started Spark: it fell back to batch 220 and re-read batch 221 onward from Kafka (retention 7 days).
4. **Verification:** every Hive row count matched its Kafka topic offset (apart from a few rows of live micro-batch
   lag), and per severity the number of distinct `raw_key` equalled the number of keyed rows (no duplicates).

## Fixes (committed)
| Commit | Change |
|---|---|
| `5eddf5d` | `hadoop-hdfs`: safe-mode wait bounded (120 s) and non-fatal, start timeout 360 s. Spark and Hive units: fatal `ExecStartPre` guard (300 s) so they fail clearly instead of crash-looping. New static + behavioural test, mutation-tested against over a dozen broken units |
| `aa814df` | `install.sh`: a failing unit no longer aborts the install; `reset-failed` before each start; real HDFS safe-mode status; non-zero exit if anything failed. Tested with stubs and 8 mutants |

## Still recommended
- Set `dfs.datanode.synconclose=true` so closed HDFS blocks are fsynced.
- Reduce NameNode/DataNode heap (≈ 1.5 GB memory available with the stack running).
- Run `install.sh` so systemd, not hand-started shells, owns the processes, then do a reboot test.
- Investigate the reset (`journalctl -b -1`, hypervisor logs, OOM).
- Delete the quarantine directory once satisfied, to bring `hdfs fsck /` back to HEALTHY.

## Lessons
- A health wait must never be allowed to kill the thing it is waiting for.
- "Active" in systemd only means the process was launched; check the service's real readiness (here, safe mode OFF).
- Check counts against the source of truth (Kafka offsets) after any recovery.
- Move suspect data aside instead of deleting it.
